# v1.2 Recommendations: Backward-Compatible Schema Improvements

**Date:** 2026-05-04
**Status:** Draft for review
**Constraint:** All changes additive. Existing v1.1 artifacts must validate without modification.

---

## Executive Summary

Eight improvement areas have been identified based on regulatory deadlines, industry shifts, and standards evolution since v1.1 was finalised (January 2026). All proposed changes are optional fields — no existing required fields change, no renames, no structural reorganisation. This document provides rationale, sources, and a recommended priority order for each.

---

## 1. AI Provenance & Generation Metadata

**Priority:** HIGH — regulatory deadline August 2026
**Recommendation:** ADOPT for v1.2

### Rationale

The EU AI Act Code of Practice (December 2025) establishes transparency obligations for AI-generated content. Article 50 requires that content generated or substantially modified by AI systems be marked as such, with machine-readable provenance. As teams increasingly use AI tools (Claude, GPT-4, Gemini) to draft personas and journeys, the schema must support declaring this provenance.

Without structured provenance fields, organisations face:
- Compliance risk when deploying AI-generated service design artifacts in EU markets
- Inability to distinguish AI-generated from human-researched personas (trust issue)
- No audit trail for AI tool usage in design processes

### Proposed Approach

Add an optional `provenance` object at the top level of all artifact schemas. Fields include `generation_method` (enum), `ai_tools_used` (structured array), `human_reviewed` (boolean), and `data_sources_consent` (boolean).

### Sources

- EU AI Act, Article 50 — Transparency obligations for AI-generated content
- EU AI Act Code of Practice (Dec 2025) — Machine-readable provenance requirements
- ISO/IEC 42001:2023 — AI management system standard (provenance as a control)

## 2. Privacy & Data Governance Metadata

**Priority:** HIGH — regulatory
**Recommendation:** ADOPT for v1.2

### Rationale

The GDPR Digital Omnibus Package (November 2025) introduces specific requirements for AI processing of special category data. Persona and journey artifacts derived from real user research may contain PII or sensitive data (health conditions, financial situations, religious beliefs). Enterprise adopters in healthcare, financial services, and government need governance metadata to classify and manage these artifacts.

Current v1.1 schemas have no way to express:
- Data classification (public/internal/confidential/restricted)
- Whether an artifact contains or is derived from PII
- What anonymisation method was applied
- Retention policies or legal basis for processing

### Proposed Approach

Add an optional `data_governance` object at the top level of all artifact schemas. This follows the same pattern as `provenance` — small teams ignore it, enterprise teams opt in.

### Sources

- GDPR Digital Omnibus Package (Nov 2025) — AI data processing requirements
- UK ICO AI and Data Protection guidance (2025) — PII in AI-generated content
- ISO 27701:2019 — Privacy information management (data classification patterns)

## 3. AI Agent Representation in Journeys

**Priority:** HIGH — industry shift
**Recommendation:** ADOPT for v1.2

### Rationale

BCG's "Golden Era of CX" report (2025) projects 56% of support interactions will use agentic AI by mid-2026. Gartner predicts 40% of customer service interactions will be fully automated by 2027. The current journey schema models human-only interactions — there is no way to express that a chatbot handles step 3, hands off to a human at step 4, or that a recommendation engine operates the product discovery channel.

This directly elevates existing backlog item BACK-003 ("Support AI agents and machine users in schema"), moving it from P4 to active development.

### Proposed Approach

Three additive changes to the journey schema:
1. `agents` array in journey context — declares AI agents participating in the journey
2. `actor` and `handoff` fields on steps — who performs each step, and how control transfers
3. `operated_by` on channels — who operates each channel at each step

### Sources

- BCG "Golden Era of CX" (2025) — 56% agentic support interactions
- Gartner "Customer Service Predictions" (2025) — 40% full automation by 2027
- MCP Specification 2025-11-25 — Agent capability declaration patterns
- Existing backlog: BACK-003

## 4. Expanded Accessibility & Cognitive Load

**Priority:** MEDIUM
**Recommendation:** ADOPT for v1.2

### Rationale

WCAG 3.0 (Working Draft, September 2025) introduces 174 new outcomes, significantly expanding cognitive disability coverage. The current persona schema has `technologyComfort` but no structured way to express physical, cognitive, or sensory accessibility needs. Journey steps have no mechanism for assessing cognitive load — a key factor in inclusive design.

Adding structured accessibility fields enables:
- Persona-driven accessibility audits of journeys
- Cognitive load mapping across journey steps
- Assistive technology considerations in channel selection
- Alignment with WCAG 3.0's expanded scope

### Proposed Approach

1. `accessibilityNeeds` object on Core Persona's `behavioural_attributes` — structured arrays for physical, cognitive, sensory needs and assistive technologies
2. `cognitive_load` object on journey steps — decision complexity, information density, time pressure

### Sources

- WCAG 3.0 Working Draft (Sept 2025) — 174 new outcomes, cognitive accessibility
- W3C Cognitive Accessibility Guidance (2025) — Pattern recommendations
- Microsoft Inclusive Design Toolkit (2025) — Cognitive load assessment frameworks

## 5. Adaptive Journey Primitives

**Priority:** MEDIUM
**Recommendation:** ADOPT for v1.2

### Rationale

The service design industry is moving from static journey maps to signal-driven, branching journey models. Platforms like Adobe Journey Optimizer, Salesforce Marketing Cloud, and Braze now treat journeys as adaptive systems that respond to real-time signals. The current schema models linear sequences only.

Adding adaptive primitives enables:
- Representing branching journeys (e.g., "if satisfaction < 3, route to recovery path")
- Declaring external signals that influence journey flow
- SLA tracking per step
- Forward compatibility with journey orchestration platforms

### Proposed Approach

1. `journey_type` enum (`linear`, `adaptive`, `orchestrated`) — existing journeys implicitly `linear`
2. `signals` array at journey level — external inputs that drive adaptation
3. `decision_point` on steps — conditional branching with target step references
4. `sla` on steps — target duration and escalation

### Sources

- Adobe Journey Optimizer documentation (2025) — Signal-driven journey patterns
- Salesforce Marketing Cloud — Journey branching models
- Gartner "Journey Orchestration" Market Guide (2025) — Adaptive journey frameworks
- Qualtrics XM — Real-time signal integration patterns

## 6. MCP-Compatible Annotations

**Priority:** MEDIUM
**Recommendation:** ADOPT for v1.2

### Rationale

The Model Context Protocol (MCP) has reached 97M+ monthly SDK downloads as of early 2026, establishing itself as the industry standard for AI tool integration. MCP annotations make content self-describing for AI tools — declaring intended audience, usage hints, and relationships between artifacts.

Adding MCP-compatible annotations enables:
- AI tools to understand what an artifact is and how to use it
- Automated discovery and filtering of artifacts
- Explicit relationship declarations between artifacts (beyond the existing `personaRef`/`roleRefs` pattern)
- Better integration with AI-powered service design tools

### Proposed Approach

Add an optional `annotations` object at the top level of all schemas with `audience`, `usage_hints`, `related_artifacts`, and `tags` fields.

### Sources

- MCP Specification 2025-11-25 — Annotation patterns and conventions
- Anthropic MCP documentation — Resource annotation best practices
- W3C Web Annotation Data Model — Annotation structure patterns

## 7. Structured Emotion Model

**Priority:** LOW
**Recommendation:** ADOPT for v1.2 (documentation + convention, minimal schema change)

### Rationale

The current emotion model uses a simple -2 to +2 integer scale (`emotional_intensity`). While effective for basic journey mapping, it cannot express the difference between "frustrated and agitated" (-1, high arousal) and "disappointed and deflated" (-1, low arousal). Dimensional models (valence-arousal) and categorical models (Plutchik's wheel) enable more nuanced emotional analysis.

Since `lane_content` already uses `additionalProperties: true`, the structured emotion model can be adopted as a documented convention without requiring schema changes. This makes it the lowest-risk improvement.

### Proposed Approach

Document a recommended structure for emotion lane content objects that supports three models:
- `simple`: existing -2 to +2 scale (default, fully backward compatible)
- `dimensional`: valence (-1 to +1) and arousal (0 to 1)
- `categorical`: Plutchik primary emotions

### Sources

- Russell's Circumplex Model of Affect (1980) — Valence-arousal dimensional model
- Plutchik's Wheel of Emotions (1980) — Categorical emotion taxonomy
- Onyx Emotion Ontology — Structured emotion representation for linked data
- Norman, D. "Emotional Design" (2004) — Emotion in design contexts

## 8. JSON-LD Context

**Priority:** LOW — strategic positioning
**Recommendation:** ADOPT for v1.2

### Rationale

No interoperability standard exists for UX research artifacts. Adding optional JSON-LD `@context` and `@type` fields positions the Digital Service Design Standards as a potential interchange format. JSON-LD is fully backward compatible — standard JSON parsers ignore `@context`, and the fields are optional.

This is a low-effort, high-optionality change:
- Enables future semantic web integration
- Supports linked data discovery across organisations
- `sameAs` on identity objects allows cross-referencing entities across systems
- Establishes namespace conventions (`.persona.json`, `.journey.json` file extensions)

### Proposed Approach

Add optional `@context`, `@type` at the top level, and optional `sameAs` on identity objects. Publish a context document at `https://schemas.digitalservice.design/context/v1.2`.

### Sources

- JSON-LD 1.1 Specification (W3C Recommendation)
- Schema.org — Linked data vocabulary patterns
- W3C Design Tokens Specification 2025.10 — Interoperability conventions for design artifacts

|-------|-------|-----------|
| **Phase 1** (immediate) | 1. AI Provenance, 2. Data Governance | Regulatory deadlines — EU AI Act Aug 2026. Lead time needed for adoption. |

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Schema bloat — too many optional fields confuse adopters | Medium | Medium | Clear documentation tiers: "start here" vs "enterprise". Progressive disclosure in tooling. |
| Validator complexity — new fields need validation logic | Low | Low | All new fields are optional. Validators only need to accept them, not require them. |
| Premature standardisation — locking in patterns that evolve | Low | Medium | All fields optional and additive. Easy to deprecate in v1.3 if patterns shift. |
| Adoption friction — existing users perceive v1.2 as complex | Medium | Low | Migration guide emphasises "do nothing" path. v1.1 artifacts remain valid. |
