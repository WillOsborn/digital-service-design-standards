**Architecture:** Three core artifact types (Actor, Mission, Experience) replace the v1.1 Persona/Role/Pairing/Journey pipeline. Declaration-driven lanes, per-field provenance, graph relationships. YAML authoring with JSON exchange. All v2.0 artifacts live under `v2.0/` alongside existing `v1.1/`.

## Background Context

### What this project is
The Digital Service Design Standards (DSDS) define structured schemas for service design artifacts — personas, journeys, and related tools. v1.1 is the current release. v2.0 is a ground-up rethink for the AI-agent era.

### Key design documents (read these first)
- `research/v2.0-exploration/vision.md` — Full vision document: architecture, design principles, structural comparison with v1.1, research validation, format recommendation, migration cost assessment
- `research/v2.0-exploration/claude-as-interface.md` — How Claude.ai/Desktop/Code serves as the design interface
- `research/plan-b-unconstrained-rethink.md` — Original research plan that drove the exploration

### v2.0 architecture (three primitives)
| Primitive | What it is | Replaces |
|-----------|-----------|----------|
| **Actor** | Unified entity with traits (enduring), contexts (situational), emergence (collision insights) | Persona + Role + Pairing |
| **Mission** | Persona-agnostic service graph — nodes, edges, phases, paths. Carries service-level data only (channels, barriers, accessibility, frontstage, backstage) | Journey (structural layer) |
| **Experience** | Persona-specific journey through a Mission — thoughts, emotions, needs, pain, persona-specific barriers | Journey (persona layer) |

Key design decisions:
- **Missions describe the service (the map). Experiences describe someone's journey through it (the trip).** One Mission supports many Experiences.
- **Lanes are declaration-driven.** Core typed lanes (channels, barriers, accessibility, emotion) are schema-validated. Extended lanes (frontstage, backstage, data-required, roles-involved, kpis) use simple types (text/list/metric) and don't require schema changes.
- **Per-field provenance** via `$provenance` wrappers (opt-in, W3C Design Tokens convention).
- **Native accessibility** on Actors (identity-level) and Mission nodes (touchpoint-level with WCAG 3.0-aligned cognitive load breakdown).
- **Governance** for EU AI Act / GDPR compliance (data classification, PII, anonymisation, legal basis).
- **Typed relationships** on every artifact for graph interoperability.
- **Per-step needs and pain** on Experience nodes — the "micro-emergence" that only exists when a specific actor meets a specific touchpoint. These are deliberately NOT in Actor or Mission — they force the design thinking.

### Risk Mitigations

The following mitigations are built into the plan based on critical evaluation:

1. **Schema consistency audit (Task 1.0)** — Before copying schemas from research, audit all three for structural consistency and run ajv compilation. Prevents rework cascade from schema bugs.
2. **David & Maria are Actor-only initially (Tasks 1.4, 1.5)** — No fabricated Missions. Missions for these personas created later via builder skills (dogfooding).
3. **Renderer spike (Task 4.0)** — Prove React Flow + ELK.js works in Claude.ai artifacts before committing to the mission-renderer.
4. **Version routing (Task 10.1)** — Define how v1.1 and v2.0 skills coexist so Claude selects the right one.
5. **Quality gates** — Sub-agent validation after each example and skill deliverable.
6. **WS2 partial blocker for WS3** — Builder skill testing requires a working validator (at least Tasks 2.1-2.3).
7. **Converter outputs quality warnings** — Flags sections needing human review; migration guide emphasises that design thinking (emergence, needAtStep, painAtStep) requires human work.
8. **Converter field renaming is explicit** — v1.1→v2.0 field mapping is NOT simple renaming. Key renames: `text`→`need` (needs), `text`→`frustration` (frustrations), `text`→`goal` (goals), `text`→`painPoint` (painPoints). Enum translations: `"persona"`→`"traits"`, `"role"`→`"context"`, `"persona+role"`→`"collision"`. Channel taxonomy: `"non_digital"`→`"physical"` (heuristic split to telecom/physical). Converter tests MUST verify field-name transformation, not just array length.
9. **Builder skill has a fast mode** — The Actor builder's 6-phase process (~50-80 questions) is impractical for most users. The skill MUST offer three modes: (a) **Full** — step-by-step through everything, (b) **Guided** — key questions only, AI fills defaults for optional fields, user reviews, (c) **Import** — user provides raw text/research, AI extracts and structures. Default to Guided mode. Full mode is for quality-critical personas.
10. **Path frequencies don't need to sum to 1.0** — Paths can overlap (the abandon path exits before the decision that splits happy/return). The validator should NOT flag frequency sums > 1.0 as errors, but SHOULD warn if the non-overlapping terminal paths (happy + return) sum to significantly more or less than 1.0.
11. **npm dependencies checked in Task 1.0** — Schema audit assumes ajv is installed. Step 0 of Task 1.0 verifies and installs dependencies.
12. **Version routing (Task 10.1) is detailed, not outlined** — Must be implemented before builder/renderer skills ship. Promotes to Phase 2a.
