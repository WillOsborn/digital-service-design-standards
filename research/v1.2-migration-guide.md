# Migration Guide: v1.1 → v1.2

**Date:** 2026-05-04
**Status:** Draft

---

## The Short Version

**You don't have to do anything.** All v1.1 artifacts validate against v1.2 schemas without modification. v1.2 is purely additive — every new field is optional. Migrate at your own pace, adopting only the fields that matter to your organisation.

---

## What Changed

v1.2 adds optional fields in 8 areas. No fields were removed, renamed, or restructured.

| Area | Schemas Affected | Effort |
|------|-----------------|--------|
| AI Provenance | All | Low — add `provenance` object when relevant |
| Data Governance | All | Low — add `data_governance` object for regulated environments |
| AI Agents in Journeys | Journey | Medium — model agent actors and handoffs |
| Accessibility | Persona, Journey | Low — add `accessibilityNeeds` to personas, `cognitive_load` to steps |
| Adaptive Journeys | Journey | Medium — add `journey_type`, `signals`, `decision_point`, `sla` |
| MCP Annotations | All | Low — add `annotations` for AI tool integration |
| Structured Emotions | Journey (convention) | Minimal — no schema change, just richer emotion data in lane_content |
| JSON-LD | All | Minimal — add `@context` and `@type` if using linked data |

## Migration Paths

### Path 1: Do Nothing (valid indefinitely)

Your v1.1 artifacts continue to validate against v1.2 schemas. The v1.2 validator accepts both `1.1.x` and `1.2.x` version strings, and both v1.1 and v1.2 standard names.

No action required. No deadline.

### Path 2: Update Version Only

If you want to signal v1.2 adoption without adding new fields:

```diff
  "schema_info": {
-   "version": "1.1.0",
-   "standard": "Service Design Persona Standard v1.1",
+   "version": "1.2.0",
+   "standard": "Service Design Persona Standard v1.2",
    "schema_type": "core-persona",
    ...
  }
```

This is optional. Both version strings validate against v1.2 schemas.

### Path 3: Adopt Regulatory Fields (recommended for EU-operating teams)

Add `provenance` and `data_governance` to your artifacts. Start with the artifacts most likely to be AI-generated or to contain PII-derived data.

```json
{
  "schema_info": { "version": "1.2.0", "..." },
  "identity": { "..." },
  "provenance": {
    "generation_method": "ai_assisted",
    "ai_tools_used": [
      { "tool": "Claude", "version": "3.5 Sonnet", "usage": "initial draft" }
    ],
    "human_reviewed": true,
    "human_reviewed_by": "Design Lead",
    "human_reviewed_date": "2026-05-01"
  },
  "data_governance": {
    "data_classification": "internal",
    "contains_pii": false,
    "anonymisation_method": "fictional_composite"
  },
  "..."
}
```

### Path 4: Adopt AI Agent Fields (for teams designing agentic journeys)

Add agent actors to your journey context and steps:

```json
{
  "journey": {
    "context": {
      "persona_context": "...",
      "agents": [
        {
          "id": "agent-support-bot",
          "name": "Customer Support Bot",
          "type": "chatbot",
          "capabilities": ["answer FAQs", "check order status"],
          "constraints": ["cannot process refunds", "must escalate complaints"],
          "autonomy_level": "semi_autonomous"
        }
      ]
    },
    "phases": [{
      "steps": [{
        "id": "step-1",
        "name": "Initial contact",
        "actor": "ai_agent",
        "handoff": {
          "from": "ai_agent",
          "to": "human",
          "trigger": "customer requests human agent"
        }
      }]
    }]
  }
}
```

### Path 5: Full Adoption

Add all v1.2 fields relevant to your context. See [v1.2-schema-snippets.md](v1.2-schema-snippets.md) for complete field definitions.

## Version String Rules

| Version | Validates Against v1.1 Schema? | Validates Against v1.2 Schema? |
|---------|-------------------------------|-------------------------------|
| `1.1.0` | Yes | Yes |
| `1.1.3` | Yes | Yes |
| `1.2.0` | No (pattern rejects) | Yes |
| `1.2.1` | No (pattern rejects) | Yes |

This is expected behaviour. v1.2 schemas are strictly wider than v1.1.

---

## Validator Changes

| Validator | v1.1 Artifacts | v1.2 Artifacts |
|-----------|---------------|---------------|
| v1.1 validator (`validate-v1.1.js`) | PASS | FAIL (new fields rejected by `additionalProperties: false`) |
| v1.2 validator (new) | PASS | PASS |

**Recommendation:** Use the v1.2 validator for all artifacts once available. It accepts both versions.

## Standard Name Changes

Each schema type has both v1.1 and v1.2 standard names accepted:

| Schema | v1.1 Standard | v1.2 Standard |
|--------|--------------|--------------|
| Core Persona | `Service Design Persona Standard v1.1` | `Service Design Persona Standard v1.2` |

## FAQ

**Q: Do I need to update my v1.1 artifacts?**
A: No. They remain valid indefinitely.

**Q: Can I use some v1.2 fields but not others?**
A: Yes. Every v1.2 field is independently optional.

**Q: Will v1.2 artifacts work with v1.1 tooling?**
A: No — v1.1 validators will reject artifacts with v1.2 fields (because `additionalProperties: false`). Use the v1.2 validator.

**Q: What about the emotion model?**
A: The structured emotion model is a documentation convention, not a schema change. `lane_content` already allows additional properties, so you can use the richer emotion structure immediately with no schema update.

**Q: Is there a v1.2 → v1.1 downgrade path?**
A: Remove any v1.2-only fields and revert the version/standard strings. Since v1.2 is additive-only, downgrading is straightforward deletion.
